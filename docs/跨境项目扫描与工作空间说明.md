# 跨境项目扫描与工作空间说明

## 扫描范围

本次按用户指定的两个本地仓库，对 master 分支进行只读静态审阅。没有切换分支、启动业务服务、连接数据库或调用渠道。没有将仓库凭据、环境配置或真实交易数据加入页面。

| 工作空间 | 仓库 | 扫描 commit | 覆盖业务 |
| --- | --- | --- | --- |
| 跨境支付 | cross-border | `32fb39352d48da0e5f76137c94e492f8a38c2083` | 跨境汇款、银行明细推送、海关申报 |
| MSO | hk-cb | `ebe71505dff18eec236557af301ada9591fa0b10` | 外币付款、境外收款人、虚拟账户 |

两个项目包含更多业务模块；本次选择六条具有明确入口和处理分支的路径展示，并非全仓业务或生产链路清单。外卡空间沿用原有三个案例，没有在本次重新扫描外卡仓库。

## 页面使用

`hk-cb` 对应的业务名称为 **MSO**。内部存储键继续使用 `hk-cb`，以兼容已有记录；页面、报告及导出使用 MSO。用户维护的 Markdown 正文不会因为更名被覆盖。

排查记录页支持关键词、处理反馈和 AI 状态筛选。报告中的有效 AI 证据引用支持点击定位原始日志，便于核验模型结论。

左侧工作空间下拉框可以切换外卡支付、跨境支付、MSO。选择业务案例会更新下方链路，点击“开始排查”查看证据、业务分支和代码来源。新空间的文档中已预填静态扫描摘要，可在服务配置中编辑并保存，也可随报告交给 AI 分析。

新增案例中的流水号、商户、金额、关联标识、事件日志均为人工构造的沙箱数据。业务步骤和判断依据来自源代码；页面事件名用于统一展示，不声称是生产日志原文。所有链路图展示可能的业务路径，不表示每个节点已经实际执行。cb_common 为共享代码模块，不应当作独立服务器。

## 数据隔离

- 外卡空间沿用原 localStorage 键，原记录无需迁移。
- 跨境支付使用 `paytrace.frontend.v1.cross-border.*`。
- MSO使用 `paytrace.frontend.v1.hk-cb.*`。
- 排查记录、服务启用配置、Markdown 和仓库配置按空间隔离。
- 本机模型连接配置共用；每次分析只携带该报告所属空间的知识与证据。
- 本次阅读 master 是开发过程中的一次性扫描，不代表页面已实现任意仓库自动扫描。运行时扫描开关仍只保存配置。

## 业务路径及代码依据

### 跨境支付 / 跨境汇款

案例：`CB202609200001` — 收款人协议过期，汇款未受理

```text
汇款申请（cb_trx） → 协议有效期校验（cb_trx） → 业务分流（cb_trx） → 汇款处理（cb_trx）
```

当前沙箱记录在收款人协议有效期校验处返回。代码中该检查位于 rmbCrossOrderBiz.rmbCross 调用之前，因此本次请求不能据此认定已向渠道发起汇款。

| 文件位置 | 方法 | 依据 |
| --- | --- | --- |
| `cb/cb_trx/src/main/java/com/helipay/app/trx/docking/controller/rmbCross/RmbCrossOrderController.java:86` | rmbCross | 收款人协议过期时直接返回，之后才调用业务层。 |
| `cb/cb_common/src/main/java/com/helipay/common/base/biz/docking/RmbCrossOrderBizImpl.java:162` | rmbCross | 依据 crossBorderSysDeal 分流到本地或远程核心；不是固定单一路径。 |

运营下一步：
- 核对收款人协议有效期及审核状态，更新资料后按业务流程重新提交。
- 检查是否存在其他请求已受理，避免重复发起同一订单。

待确认：
- 此处只能确认当前请求被校验拦截，不能确认商户其他提交的结果。

### 跨境支付 / 银行明细推送

案例：`CB202609200002` — 明细文件已生成，银行上传失败

```text

```

任务已生成文件并进入 DOING，随后银行上传响应非成功，沙箱记录为 FAIL。源码显示上传响应决定最终 pushStatus，文件生成成功本身不能证明银行已接收。

### 跨境支付 / 海关申报

案例：`CB202609200003` — 申报已发送，回执状态未更新

```text
申报请求（cb_trx） → 创建报关单（cb_trx） → 定时查单（cb_daemon） → 渠道查询（cb_daemon） → 条件重试（cb_daemon）
```

沙箱查询记录仍为 DOING，且未到自动重试间隔。源码只有在状态一致时检查重试配置及间隔；支付结果和申报结果应分别核实。

| `cb/cb_daemon/src/main/java/com/helipay/app/daemon/controller/job/applycustoms/ApplyCustomsOrderQueryTimer.java:51` | execute | 筛选未完成订单，调用 channelQuery。 |

运营下一步：
- 通过申报流水号定位报关订单和渠道请求记录，查询最新回执。

### MSO / 外币付款

案例：`HK202609200001` — 付款主单扣款中，部分明细尚未完成

```text
确认付款（cb_merchant_api） → 余额与状态检查（cb_merchant_api） → 明细扣款队列（cb_daemon） → 明细处理（cb_daemon） → 主单汇总（cb_daemon）
```

源码在主单 DEBITING 状态下统计 INIT 明细；数量不为零时直接返回等待下次查询更新。当前记录符合该分支，不能仅凭主单状态判断整批失败。

运营下一步：

### MSO / 境外收款人


创建收款人会生成渠道报备任务和通知记录。当前消费记录显示获取锁超时，未在本次尝试进入 doChannelReport；ACTIVE 不能替代渠道报备结果。

### MSO / 虚拟账户

案例：`HK202609200003` — 开户回调已到，渠道交互记录未匹配

```text
开户申请（cb_trx） → 创建交互记录（cb_trx） → 异步渠道交互（cb_daemon） → 开户状态回调（cb_trx） → 账户状态完成（cb_trx）
```

源码在 VA 为 DOING 时，按渠道和 bizId 查询 ChannelInterflow；找不到时抛出订单不存在异常，无法进入 applyECheckComplete。沙箱案例对应这一分支。

| 文件位置 | 方法 | 依据 |
| --- | --- | --- |
| `cb/cb_trx/src/main/java/com/helipay/app/trx/web/controller/va/VirtualAccountController.java:59` | applyECheck | 调用 VirtualAccountManagerService。 |
| `cb/cb_common/src/main/java/com/helipay/common/base/service/va/VirtualAccountManagerServiceImpl.java:122` | applyECheck | 限定 USD、US、EDUCATION；提交后发送渠道交互消息。 |
| `cb/cb_daemon/src/main/java/com/helipay/app/daemon/listener/sunrate/ChannelInterflowListener.java:1` | ChannelInterflowListener | 异步渠道交互消费者；回调到达是另一条入口，不代表同步调用。 |
| `cb/cb_common/src/main/java/com/helipay/common/base/service/va/VirtualAccountManagerServiceImpl.java:429` | VAStatusChange | DOING 时按渠道和 bizId 查询交互记录，缺失则抛错。 |

运营下一步：
- 核对 bizId、渠道编码、VA 记录及开户交互记录是否一致。
- 追踪开户事务提交后的消息发送和 ChannelInterflow 处理过程。
- 确认真实渠道开户结果后再评估修复；避免重复开户或手工伪造成功状态。

待确认：
- 当前缺少渠道最终开户状态，不能仅凭回调到达认定账户已可用。
- 该扫描入口是特定的 applyECheck 路径，不能推广到所有 VA 产品。
