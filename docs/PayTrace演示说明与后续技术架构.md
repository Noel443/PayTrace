## 第一部分：原型演示文档

### 1. 产品定位

PayTrace 面向支付运营，目标是让运营通过交易流水号和问题描述，自助获取交易处理情况、关联日志、异常原因及下一步处理建议。

核心业务路径：

```text
运营输入交易流水号与问题
    → 查询交易信息
    → 检索交易服务日志
    → 提取关联标识，追踪下游服务
    → 结合业务规则与代码分析
    → 输出结论、证据和待确认事项
    → 运营处理或转交开发
    → 记录最终反馈
```

产品希望减少开发在重复查单、查日志、解释业务流程上的时间，也让需要开发介入的问题携带完整证据，而不只是收到一句“这笔交易有问题”。实际节省时间和开发介入比例需要后续试点测量。

### 3. 启动与展示

#### 3.1 直接打开页面

打开项目中的 `frontend/index.html` 即可体验。该方式适合快速查看页面。

#### 3.2 本地 HTTP 访问

已安装 Node.js 时，在项目根目录执行：

```bash
npm start
```

访问：`http://127.0.0.1:5173`。

不需要执行 `npm install`。该命令只启动静态文件服务，不是业务后端。端口被占用时，可在 macOS/Linux 终端执行：

```bash
PORT=5174 npm start
```

#### 3.3 通过 ngrok 给评委体验

提前安装并完成 ngrok 账号配置。本地服务保持运行，另开终端执行：

```bash
ngrok http 5173
```

将 ngrok 提供的 HTTPS 地址分享给评委。当前页面没有登录功能，只适合公开模拟数据；不要录入生产交易或敏感信息。

每位评委的排查记录保存在各自浏览器，不会汇总到演示者电脑。不同访问地址的记录也不共享。清理站点数据后记录会被删除；浏览器存储不可用时会退化为页面内存，刷新后丢失。

### 4. 演示前准备

1. 打开“服务配置”，确认 trx 和 daemon 均已启用并保存。
2. 返回“交易排查”，确认三个演示场景正常显示。
3. 首次演示建议使用独立浏览器配置或干净的站点存储，避免历史反馈干扰展示。
4. 明确介绍当前是前端原型，重点验证运营流程、证据表达和处理闭环。

#### 5.1 操作步骤与讲解要点

| 步骤 | 页面操作 | 预期结果与讲解要点 |
| --- | --- | --- |
| 1 | 点击“支付成功，商户未收到通知”样例 | 自动填入交易流水号及问题描述；点击样例只填充表单，不自动排查 |
| 2 | 点击“开始排查” | 显示交易概况与排查报告 |
| 3 | 查看诊断结论 | 显示“支付已成功，商户通知重试耗尽” |
| 4 | 展开 trx 日志证据 | 看到支付成功记录，以及向 daemon 投递消息的 MSG77662 |
| 5 | 展开 daemon 日志证据 | 看到同一消息的三次通知超时和 RETRY_EXHAUSTED |
| 6 | 展开通知重试策略 | 展示三次未确认后进入人工复核的演示规则 |
| 7 | 查看“运营下一步”和“仍需确认” | 提示核实商户接口、订单状态和幂等处理；不会将超时直接等同于商户未处理 |
| 8 | 点击“导出排查单” | 下载包含问题、结论、证据、建议及已有反馈的 Markdown 文件 |
| 9 | 选择处理结果，填写备注并保存 | 可选择“已解决”“需要开发介入”“判断不正确” |
| 10 | 进入“排查记录”并打开记录 | 查看保存的报告及反馈，形成原型中的处理闭环 |

日志上下文可能混入其他交易。演示中应强调：相邻日志只用于辅助阅读，不能因为位置接近就作为本笔交易的证据。

导出排查单后产生的反馈不会自动写回已下载文件；需要包含最新反馈时，再次导出即可。

#### 5.2 主案例建议讲解词

> 运营只需要输入交易流水号。系统先确认交易状态，再从交易服务日志中提取消息 ID，关联到异步通知服务，最后给出有日志依据的结论和处理建议。当前演示使用浏览器样例数据，后续会将这套流程接到真实交易查询、日志平台和 AI 分析服务。

### 6. 补充场景

| 场景 | 操作 | 预期结果 | 要验证的业务原则 |
| --- | --- | --- | --- |
| 渠道明确拒绝 | 查询 T202609200002 | 返回“渠道返回拒绝，具体发卡行原因待确认” | 通用拒绝码不能直接解释为余额不足；05 的含义仅为演示映射 |
| 渠道超时 | 查询 T202609200003 | 返回“渠道请求超时，最终支付状态未知”，标记待核实 | 超时不等于失败，不能直接建议重复付款 |
| 下游日志缺失 | 关闭 daemon 并保存，再查询 T202609200001 | 返回证据不足，无法确定异常原因 | 缺少证据时不应给出确定结论 |
| 未知流水号 | 输入不属于三个样例的流水号 | 提示未找到演示交易 | 当前原型不查询真实交易 |

完成日志缺失场景后，重新启用 daemon 并保存，恢复主演示环境。历史报告保存的是当时结果，不会因开关改变而重新计算。

## 第二部分：后续技术架构与实施规划

### 9. 建设目标与原则

后续将前端原型升级为 Java 服务，接入企业已有的交易、日志、代码和工单系统。首先把外卡支付的一条排查路径打通，再通过数据源适配器和项目配置扩展其他支付业务。

设计原则：

- 以交易和证据为中心，每个关键结论都能追溯到数据来源。
- AI 提出假设、选择受控工具、解释证据；后端执行实际查询和权限校验。
- 先只读排查和人工复核，再评估是否接入经授权的业务操作。
- 优先复用现有日志平台、身份系统及业务查询接口。
- 第一阶段采用模块化单体，确认规模瓶颈后再拆分服务。

### 10. 目标整体架构

```text
运营 Web / 后台配置页面
            |
            v
Java 应用：认证授权、任务管理、报告、反馈、审计
            |
            v
排查编排：规则判断、AI 工具调用、预算与停止条件
            |
    +-------+-------------+-------------+-------------+
    |                     |             |             |
交易查询适配器       日志检索适配器  代码/知识检索   工单适配器
    |                     |             |             |
业务查询 API         ELK / Loki       Git 仓库      企业工单平台
只读数据库           受控 SSH         业务手册      后续协作系统
                                      错误码

支撑能力：PostgreSQL、模型网关、凭据管理、监控与审计
```

模型通过应用的模型接入层调用，不能直接访问 SSH 凭据、数据库密码或无限制执行命令。

### 11. 推荐技术选型

| 层次 | 建议技术 | 选型说明 |
| --- | --- | --- |
| 当前前端 | HTML、CSS、JavaScript | 已满足原型验证，不必立即迁移 |
| 后续前端 | Vue 3、TypeScript、Element Plus，可选 | 页面和配置复杂度上升后再采用 |
| Java 后端 | Java 21 + Spring Boot 3.x | 选择团队支持的具体版本；现有本机为 Java 17，升级前需核对运行环境 |
| AI 接入 | Spring AI 或统一模型客户端 | 按 Spring Boot 兼容矩阵确定版本，封装模型差异 |
| 模型服务 | 企业模型网关或本地 Ollama | 根据数据要求、效果、成本和延迟选择；当前均未接入 |
| 业务与配置存储 | PostgreSQL | 保存任务、配置、证据元数据、报告与反馈 |
| 日志平台 | Elasticsearch、Loki 等现有平台 | 优先使用现有索引及查询能力，不重复建设日志平台 |
| SSH 访问 | SSHJ 等受控客户端 | 无集中日志时的兼容接入方式 |
| 代码版本 | Git 仓库与部署版本映射 | 按实际部署 commit 查代码，避免混用最新分支 |
| 任务进度 | 异步任务 + SSE | 前端展示真实执行进度，支持刷新后重新获取任务 |
| 初期部署 | Docker Compose | 便于开发和测试，生产适配现有发布平台 |

Redis、消息队列、向量数据库不作为首版强制依赖。任务量、检索质量和部署规模证明有需要后再引入。

### 13. 多项目、多服务器配置模型

```text
项目：外卡支付
  环境：测试 / 生产
    服务：trx
      节点：实例 A、实例 B
      日志来源：集中日志索引或 SSH 路径
      代码来源：仓库 + 目录 + 部署 commit
      关联字段：交易号、traceId、渠道流水号、消息 ID
    服务：daemon
      节点：实例 C、实例 D
      日志来源：集中日志索引或 SSH 路径
      代码来源：仓库 + 目录 + 部署 commit
      下游关系：商户通知
```

服务与服务器不能简单一一绑定：同一服务可能有多个实例，滚动发布时也可能同时存在多个代码版本。配置需要记录实例、版本及生效时间，排查时选择与交易发生时间对应的版本。

| 配置对象 | 主要字段 |
| --- | --- |
| 项目 | 项目标识、业务说明、负责人、可访问人员 |
| 环境 | 环境标识、数据范围、访问策略 |
| 服务 | 服务名称、业务职责、上游下游、关联字段规则 |
| 节点 | 主机或实例标识、归属服务、部署版本、有效时间 |
| 日志源 | 类型、索引或目录、时间格式、时区、轮转规则、凭据引用 |
| 交易源 | 查询接口或模板、允许参数、字段映射、权限过滤 |
| 代码源 | 仓库、子目录、分支参考、部署 commit、访问凭据引用 |
| 模型配置 | 模型、网关、超时、调用预算、允许的数据范围 |

不同项目复用统一排查框架，但仍需要接入字段映射、业务流程和错误码。不能只填服务器地址就自动准确理解所有项目。

### 14. 外部系统接入方案

#### 14.1 交易数据

优先对接业务已有的只读查单 API。如果只能连接数据库，使用审批过的参数化 SQL 模板和只读账号，不让 AI 自由生成并直接执行 SQL。

统一返回交易号、商户号、金额币种、状态、时间、渠道流水号及可用关联标识。查询必须带项目、环境和商户权限范围，避免不同环境或商户流水号碰撞。

#### 14.2 日志平台与 SSH

统一日志查询输入：项目、环境、服务、时间窗、标识类型、标识值和返回上限。

集中日志平台适配器通过平台 API 查询。SSH 适配器只允许访问配置目录，执行后端构造的固定检索操作，并处理多实例、轮转文件、压缩日志、超时和输出截断。

`grep -F` 可用于固定字符串初筛，但最终仍需按结构化标识或字段边界验证归属。先返回命中位置和少量上下文，需要时再展开；不默认将每个命中点前后 200 行全部送给模型。

日志工具响应应包含命中行、上下文、来源、检索时间范围、是否截断、哪些实例失败。必须区分“没有命中”“无权限”“数据源不可用”和“查询未完成”。

#### 14.3 代码与业务知识

接入 Git 后，按部署 commit 检索错误码、日志语句、异常类型及相关方法，再结合业务手册解释具体分支。第一阶段优先使用文本、符号和规则检索，检索效果需要时再增加向量能力。

找不到实际部署版本时，在报告中明确说明版本不确定，不能把其他版本的逻辑视为已证实事实。

#### 14.4 工单与协作平台

第一阶段保留 Markdown 导出。后续在用户明确点击提交后创建工单，传入交易摘要、证据链接、已确认事实、待核实事项和负责人。

工单同步必须具备提交状态、失败重试和幂等标识，避免重复建单。已确认的处理结果经审核后再进入案例库。飞书文档或消息推送是后续可选集成，不是当前能力。

### 15. AI 如何参与排查

建议分两阶段引入：

1. 固定取证流程 + AI 补充分析：先由后端查询交易和关联日志，再让模型解释证据、补充待确认事项，验证模型效果。
2. 受控自主编排：模型根据现有证据选择下一项工具调用，后端校验参数和权限后执行，并记录每次调用。

计划开放的工具包括：

| 工具 | 作用 | 主要约束 |
| --- | --- | --- |
| queryTransaction | 查交易基本信息 | 项目、环境、商户权限、只读 |
| searchLogs | 检索指定服务与时间范围日志 | 服务白名单、精确标识、条数与耗时上限 |
| expandLogContext | 展开某条证据附近日志 | 只能展开已授权来源、限制范围 |
| searchCode | 查询部署版本相关代码 | 仓库范围、commit、片段上限 |
| searchKnowledge | 获取错误码、流程、案例 | 项目匹配、版本与审核状态 |

模型不能自行拼接任意 shell 命令、访问任意主机或执行支付操作。日志、代码注释和问题描述作为待分析数据处理，其中出现的指令不得改变系统权限或工具规则。

设置最大步骤、单次工具超时、总任务超时、输出上限及模型预算。证据充分、预算耗尽或数据源不可用时结束任务，保留已经获得的证据并说明缺口。

### 16. 排查任务与报告设计

任务执行状态与业务判断分开管理：任务执行完成，不代表问题已经确认。

| 类型 | 建议取值 |
| --- | --- |
| 执行状态 | QUEUED、RUNNING、COMPLETED、PARTIAL、FAILED、CANCELLED |
| 诊断结果 | 已定位、待核实、证据不足 |
| 运营反馈 | 未反馈、已解决、需要开发介入、判断不正确 |

生产报告建议包含：

- 交易概况、运营问题和查询时间范围。
- 已确认事实、推测原因及待核实事项，分别展示。
- 每条关键结论引用的证据编号。
- 日志平台定位信息，或文件、实例、行号与时间等来源信息。
- 相关代码 commit、业务规则及知识版本。
- 下一步建议、适用角色和人工复核要求。
- 工具失败、截断、缺失数据源及其他覆盖限制。
- 处理反馈、工单号和审计记录。

原始敏感数据应在进入模型前脱敏，证据保存与查看都要经过权限控制，并设置保留期限。

### 17. 前后端 API 演进建议

以下为目标接口建议，当前浏览器模拟函数不代表这些 HTTP 接口已经上线。

| 接口 | 用途 |
| --- | --- |
| POST /api/investigations | 创建排查任务，返回 taskId 和初始状态 |
| GET /api/investigations/{id} | 获取任务状态、部分结果或最终报告 |
| GET /api/investigations/{id}/events | SSE 订阅真实执行进度 |
| POST /api/investigations/{id}/cancel | 取消尚未结束的任务 |
| GET /api/investigations | 按权限、时间及状态分页查询历史 |
| POST /api/investigations/{id}/feedback | 保存处理反馈 |
| GET /api/investigations/{id}/export | 导出完整排查单 |
| POST /api/investigations/{id}/tickets | 经用户确认后创建工单 |
| /api/projects、/api/services、/api/data-sources | 配置项目、服务和数据源，具体管理接口后续细化 |

创建任务时提交项目、环境、交易流水号、时间范围及问题描述。后端返回可重连的任务 ID；SSE 中断后可以重新订阅或查询任务。生产环境增加幂等请求标识、权限检查、限流和审计。

前端迁移时保留主要页面，将 `frontend/mock-api.js` 替换为真实 API 客户端，并将一次性返回结果的交互调整为异步任务状态展示。

### 18. 部署路径

| 阶段 | 部署方式 | 数据范围 |
| --- | --- | --- |
| 当前原型 | 本地 HTML 或 Node 静态服务，可通过 ngrok 展示 | 浏览器模拟数据 |
| 后端验证 | 本地 Java + 测试数据库 + 测试日志源 + 可选模型 | 脱敏或模拟数据 |
| 业务试点 | 企业测试或受控内网环境，接入统一身份 | 经批准的只读数据 |
| 生产服务 | 企业发布平台、集中配置和凭据管理、监控与备份 | 严格按角色和业务范围授权 |

ngrok 用于演示入口，不作为生产访问架构。浏览器只访问应用服务，不直接持有数据库、SSH 或模型密钥。

### 19. 分阶段实施与验收

| 阶段 | 建设内容 | 完成标准 |
| --- | --- | --- |
| P0：前端原型 | 当前三个案例、证据展示、导出、反馈和服务开关 | 运营认可页面与业务流程；明确模拟边界 |
| P1：真实取证 | Java API、只读交易查询、一个日志适配器、任务与报告持久化 | trx 到 daemon 能基于实际测试日志关联；无数据、超时、权限不足分别处理 |
| P2：AI 分析 | 模型接入、代码版本检索、证据引用、异常降级 | 关键结论可追溯；无证据时不编造；模型失败仍保留取证结果 |
| P3：受控编排 | 动态选择下游服务、多数据源和调用预算 | 每一步工具调用可审计；错误关联与循环查询有防护 |
| P4：业务试点 | SSO、细粒度权限、脱敏、工单和人工复核 | 在限定业务范围内完成实际处理闭环并获得效果数据 |
| P5：生产与扩展 | 运维保障、多项目接入、性能与成本优化 | 满足内部上线要求，新项目通过配置和适配器接入 |

首个后端版本优先打通“支付成功但商户通知失败”，不必一开始接入所有渠道、日志平台和代码仓库。

### 20. 效果评估与主要风险

| 评估项 | 评估方法 |
| --- | --- |
| 首次有效结论耗时 | 对比运营原有流程与工具辅助流程的实际耗时 |
| 开发介入比例 | 在同类工单样本中统计仍需开发参与的比例 |
| 证据准确性 | 人工核查是否混入其他交易、环境或版本的证据 |
| 诊断正确性 | 用人工确认结果核对系统结论，同时记录错误确定性判断 |
| 信息完整度 | 核查升级给开发的排查单是否包含足够交易、日志和关联信息 |
| 模型成本与延迟 | 按任务记录调用次数、Token、费用和整体延迟 |

前端预设案例不能用于证明模型正确率或实际降本收益。上述指标在真实接入和受控试点后测量。

| 风险 | 处理方向 |
| --- | --- |
| 不同服务没有统一 traceId | 建立交易号、渠道流水号、消息 ID 等关联规则，并标记关联依据 |
| 日志缺失或被截断 | 展示检索覆盖情况，返回证据不足，不自动推断业务未执行 |
| 多实例或时钟差异 | 统一时间表示，记录时区，按可配置时间窗检索并核对实例 |
| 代码与部署版本不一致 | 记录部署 commit 和生效时间，不能确认时显式说明 |
| AI 输出不可靠 | 结构化输出、证据引用校验、人工复核、回归案例与降级策略 |
| 敏感数据外发 | 查询范围控制、模型前脱敏、使用批准的模型网关 |
| 新项目理解成本高 | 明确接入清单，由业务负责人确认流程、字段和错误码映射 |

### 21. 后续接入前需要确认的信息

1. 外卡交易的只读查询入口、主键规则和状态字段含义。
2. trx、daemon 的真实职责、调用关系及消息关联字段。
3. 日志位于服务器文件还是集中日志平台，日志格式与保留周期是什么。
4. 服务节点与部署版本如何获取，Git 仓库及代码权限如何申请。
5. 可用模型服务、允许输入的数据范围及成本要求。
6. 运营可自行处理的事项与必须转交开发的边界。
7. 已有身份、权限、工单和审核系统的对接方式。

下一步以这些信息为依据，确认首个真实场景的数据接入合同和验收样本，再开始 Java 后端实现。
