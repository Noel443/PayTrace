# PayTrace 支付业务智能排障助手

> 让运营少等研发，让研发少翻日志，让交易问题有据可查。
>
> 参赛方向：AI 工具类 · 支付业务研发与运营提效
>
> 建议节奏：文档讲解约 4 分钟，随后原型演示约 3 分钟。附录用于评审查阅，无需现场逐条讲解。

## 一、业务需求：为什么要做？（约 45 秒）

支付异常排查中，最耗时的往往不是修复，而是找到信息、串起链路、等待相关人员处理。

1. **多服务器日志分散，开发排查费劲。** 一笔交易可能经过交易服务、异步任务、渠道交互等环节。研发需要切换多台服务器和日志文件，再用交易号、消息 ID 等标识逐步关联，才能判断问题出现在哪里。
2. **运营依赖研发，问题容易卡在等待。** 商户反馈“客户已扣款，订单还在处理中”，运营往往无法自行判断。研发忙于需求或其他故障时，运营只能等待，商户也迟迟得不到有效答复。
3. **排查经验依赖个人，同样的问题反复查。** 日志需要结合业务流程理解；人员交接时，还要重新解释查询过程、判断依据和待确认事项。

**建设目标：让运营在授权范围内完成常见问题的初步排查，让研发接手复杂问题时直接拿到证据与上下文。**

## 二、核心功能：平台能做什么？（约 55 秒）

| 功能点 | 解决的问题 | 当前原型能力 |
| --- | --- | --- |
| 交易排查入口 | 查询入口分散，排查步骤重复 | 输入样例交易号，查看交易状态、日志证据和处理建议 |
| 服务器日志数据源 | 多台服务器、多份日志难以管理 | 按工作空间配置多个数据源，逐个测试 SSH 连接、按标识查询指定日志文件 |
| 交易证据图谱 | 日志看到了，但业务链路不清楚 | 展示业务节点、异常与证据缺口，点击节点查看关联原文 |
| AI 证据分析 | 运营难以理解技术日志，研发解释成本高 | 结合问题、样例证据与业务文档，输出事实、可能原因、待核实事项和下一步建议 |
| 业务知识与项目分析 | 业务知识分散，新人理解成本高 | 导入 Markdown；可选读取 Git 指定分支的部分代码，由 AI 生成静态业务链路 |
| 补证与报告沉淀 | 信息补齐后结论难更新，交接容易遗漏 | 样例补证后更新结论，保存排查记录、处理反馈，并导出 Markdown 报告 |

**已覆盖外卡支付、跨境支付、MSO 三个工作空间，共九个样例案例。**

当前交易排查使用模拟数据；SSH 日志查询可连接可达服务器，但尚未自动合入交易报告，也未实现真实交易的跨服务器自动追踪。

## 三、创新点与亮点：价值体现在哪里？（约 60 秒）

### 1. 把技术日志转化为业务上可理解的问题

- 围绕“支付是否成功、通知是否确认、商户订单是否完成”分别展示状态。
- 帮助运营理解当前进展，也让研发快速找到需要深入排查的环节。
- **业务价值：减少运营与研发之间反复翻译日志的沟通。**

### 2. AI 分析带证据，结论可以回查

- 将日志组织为证据图谱，明确哪些节点异常、哪些节点还缺信息。
- AI 分析中的有效证据引用可以点击回到日志原文，方便人工核实。
- **业务价值：让使用者知道判断依据，避免把推测直接当成事实。**

### 3. 新证据进入后，结论能够修订

- 例如：平台支付成功、通知超时，此时商户订单状态仍需核实。
- 补充“商户订单已完成”后，更新商户状态和处理建议，同时保留通知异常及补证前后对照。
- **业务价值：排查可以持续推进，避免拿着过期结论继续处理。**

### 4. 业务知识可配置，排查经验可复用

- 按工作空间维护业务文档、服务配置和排查记录，可选结合代码生成业务链路。
- 支持多套模型配置，可选择兼容接口或本地 Ollama。
- **业务价值：便于适配不同支付业务，也为团队沉淀排查经验。**

## 四、方案架构：如何实现？（约 25 秒）

按“业务入口—证据组织—AI 辅助—结果交接”组织能力：

| 层次 | 主要职责 |
| --- | --- |
| 业务入口 | 工作空间、交易号、问题描述、服务器数据源配置 |
| 证据与知识 | 日志及标识关联、业务文档、项目静态链路、补充证据 |
| 分析展示 | 规则判断、证据图谱、AI 分析、待核实事项 |
| 协作交接 | 排查记录、处理反馈、Markdown 报告 |

**当前实现：浏览器页面＋本地 Node 服务＋可配置模型。** 本地服务提供 SSH 查询、项目分析和模型调用；样例证据关联由规则完成。生产阶段再打通真实交易查询与多节点日志的自动关联。

## 五、可行性与预期价值（约 35 秒）

1. **技术可行：已有可演示原型。** 样例排查、证据图谱、真实模型调用、独立 SSH 查询、报告导出等能力已实现，可在此基础上逐步接入业务系统。
2. **落地可控：先从高频场景试点。** 优先选择“支付成功但通知异常”等问题，打通真实交易查询和多节点只读日志检索，再扩大覆盖范围。
3. **收益可衡量：关注等待与重复劳动。** 试点记录首次有效结论耗时、研发介入比例、问题处理时长和证据关联准确率；当前尚无生产实测收益数据。
4. **成本可评估：按实际使用量核算。** 主要投入包括业务接口适配、日志检索、模型调用及权限审计建设。试点测量单次排查耗时和模型用量，再决定部署规模。
5. **数据合规：采用模拟或脱敏数据。** 演示使用模拟交易与日志；涉及用户决策的 AI 输出必须人工复核。生产接入需补齐身份认证、权限控制、脱敏、凭据托管与操作审计。

## 附录一：原型演示顺序（约 3 分钟）

1. **发起排查（30 秒）。** 进入“外卡支付”，选择“支付成功，商户未收到通知”，点击“开始排查”。说明运营可以从交易问题直接进入排查。
2. **查看证据图谱（40 秒）。** 点击通知处理节点，展开日志原文。强调：支付成功和通知异常可以同时存在，商户是否完成订单仍需证据。
3. **展示 AI 分析（60 秒）。** 点击“AI 分析”，展示分析结果及有效证据引用。说明系统结合业务知识解释现有证据，复杂判断仍需人工复核。
4. **补证更新结论（30 秒）。** 选择“商户订单已完成”，补充证据并更新结论，展示前后变化。说明补证后旧 AI 分析失效，需要基于新证据重新分析。
5. **导出并交接（20 秒）。** 展示 Markdown 报告导出和历史记录，说明研发可以带着证据继续处理。

> 演示前完成模型连接测试并预先排练。若现场模型超时，继续展示规则报告、图谱与补证流程，并说明该次 AI 请求未完成。服务器配置和项目分析可用于答疑时补充展示。

### 当前能力与后续计划

- **已实现：** 三个工作空间九个样例案例、证据图谱、补证修订、真实 AI 调用、业务文档、静态项目链路分析、独立 SSH 日志查询、历史反馈与报告导出。
- **尚待打通：** 真实交易查询、多服务器自动检索与标识关联、远程日志自动进入分析报告、真实商户查单。
- **生产建设项：** 服务端身份与权限、集中持久化、多人协作、凭据托管、数据脱敏和审计。当前本地登录为演示入口，不具备生产鉴权能力。
- **决策边界：** AI 提供分析与建议，涉及用户决策的输出经人工复核；原型不执行扣款、退款或交易状态修改。
